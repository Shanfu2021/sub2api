# Upstream v0.1.151 Merge Design

## Goal

Merge the latest official `Wei-Shaw/sub2api` main branch into this fork while preserving the fork's agent, enterprise, delegated-group, income, purchase-information, and scheduling capabilities. Security, authentication, billing, and data-consistency fixes from upstream take precedence where behavior overlaps.

The integration result will be published to `Shanfu2021/sub2api` on a correctly spelled `my_feature` branch. Compilation, full tests, security scans, and image builds run on GitHub Actions rather than on this host.

## Baseline

- Customized source: local `my_featrue` at `21dd6492`.
- Previously merged upstream baseline: `d3acd8e9`.
- New upstream target: `upstream/main` at `e316ebf5` (v0.1.151 plus 17 commits, 2026-07-10).
- Divergence: 115 fork-only commits and 432 upstream-only commits.
- Expected overlap: 117 paths changed on both sides, with 35 direct text-conflict files plus two upstream-deleted locale files that require semantic migration.
- Existing untracked deployment, dump, and diagnostic files are outside scope and must not be staged or modified.

## Integration Strategy

Create `my_feature` from the current customized HEAD and merge `upstream/main` with a merge commit. Do not rebase the 115 custom commits and do not rebuild the fork by cherry-picking onto a clean upstream branch.

Resolve conflicts by behavior and ownership boundary:

1. Adopt the upstream file layout after its service, repository, gateway, and i18n splits.
2. Preserve upstream security and correctness semantics.
3. Port fork behavior into the new upstream-owned modules instead of restoring obsolete monolithic files.
4. Rebuild generated Ent and Wire outputs from the combined schema and provider graph rather than choosing generated files from either side.
5. Keep already deployed fork migration files byte-for-byte stable.

## Required Upstream Behavior

The merge must retain, at minimum, these upstream fixes:

- Gemini `/v1beta` API key authorization, IP ACL, exclusive-group, expiry, and quota enforcement (`29a5fcd2`).
- Payment fulfillment, redemption balance/concurrency atomicity, subscription-window CAS, and cache consistency (`fc66a30f`).
- Usage-log queue backpressure and synchronous fallback that prevent silent record loss (`a1b2b32e`).
- AWS EventStream vulnerability remediation for `GO-2026-5764` (`a4f942d8`).
- Go 1.26.5 toolchain upgrade for the standard-library TLS vulnerability (`25a71696`).
- Image-generation namespace permission enforcement (`a02700c1`).
- HTML escaping and URL sanitization for site name, logo, and documentation links (`bfb827b8`, `15c59be7`).
- Header-override denylist hardening (`31b6e0d9`).
- Batch-image billing, frozen-balance, queue atomicity, state-machine, and download-host hardening (`80a229bc`).
- Refund pending-state correctness, Grok per-second billing, and registration quota snapshot fixes (`76e0d907`, `d4952154`, `185f9c99`).

When a fork behavior conflicts with one of these fixes, retain the upstream safety invariant and adapt the fork feature around it.

## Required Fork Behavior

The integration must preserve these capabilities and their authorization boundaries:

### Agent Management

- One active agent level (`agent_level1`); do not restore the retired level-2 role.
- Direct parent ownership, root-admin shared capacity, agent concurrency/RPM pools, direct-user creation, invitation defaults, promotion, detachment, deletion, and return-to-root semantics.
- Agent-scoped management and usage views without exposing upstream account details.

### Delegated Groups

- Exclusive group delegation, invite defaults, effective per-user multipliers, batch rollout/rate/revoke operations, descendant cleanup, and minimum-rate propagation.
- API keys and downstream UI expose effective downstream rates only, not upstream cost rates.

### Enterprise Management

- Enterprise capacity pools, employee creation/import, balance transfer ledger, concurrency/RPM allocation, default groups, deletion resource return, and disable/delete cascading.
- Employees remain blocked from payment, redemption, invitation, subscription, and purchase-information management workflows.

### Income And Operations

- Usage records snapshot agent owner, user multiplier, agent cost multiplier, and income for direct users, enterprises, and enterprise employees.
- Admin agent tree, scoped usage, settlement targets, manual adjustments, direct-child notes, and existing low-rate income semantics remain covered by tests.
- Group `weighted` and `strict_priority` scheduling remains available alongside upstream advanced OpenAI scheduling.
- Scheduled tests may automatically update `schedulable` after failure or first-token timeout.
- Upstream error locations remain redacted.

### Purchase Information

- Root and agent purchase cards, inheritance from the direct upstream owner, admin/agent management, user/enterprise read-only access, and employee denial remain intact.

## Schema And Migration Rules

- Merge fork fields from `user`, `group`, `usage_log`, and `agent_group_delegation` schemas with upstream account shadowing, frozen balance, peak-rate, media, and batch-image schemas.
- Preserve all existing `*_hzz_*` migration filenames and contents because production migration history keys and checksums use the complete filename.
- Accept interleaved numeric prefixes from upstream migrations 154 through 173. The runner sorts and records complete filenames, so prefix reuse alone is not a reason to rename deployed migrations.
- Run the combined migration chain against real PostgreSQL in GitHub integration tests and verify idempotence and schema currency.
- Generate Ent code only after the combined schemas are final. Generate Wire output only after the combined provider graph is final.

## Conflict Resolution Areas

The highest-risk conflict groups are:

- Ent schemas and generated code.
- Authentication, registration, API-key cache, redemption, payment, and user deletion.
- Usage persistence, billing snapshots, frozen balance, and agent income.
- Gateway scheduling, strict priority, OpenAI routing, and header redaction.
- Dependency injection and generated Wire output.
- Frontend routes, sidebar permissions, auth state, shared types, account/group/usage screens, and modularized locales.
- Docker and Go toolchain versions.

Each group must be resolved against both the relevant upstream regression tests and the fork-specific tests. A compiling merge is not sufficient evidence that the behavior is preserved.

## Verification And Build Flow

Local work is limited to merge resolution, code generation required for checked-in outputs, conflict-marker checks, formatting, and other lightweight static checks. Do not run the full frontend build or full local test suite on this host.

After pushing `my_feature` to `Shanfu2021/sub2api`:

1. Wait for the `CI` workflow to complete Go unit/integration tests, frontend typecheck and critical Vitest, and golangci-lint.
2. Wait for `Security Scan` to complete `govulncheck` and the frontend production dependency audit.
3. Fix failures on the same branch and repeat until both workflows pass for the exact integration commit.
4. Trigger `HZZ Image` with `workflow_dispatch` using ref `my_feature` so the image is built in the user's GitHub repository.
5. Confirm the image workflow succeeds for the same commit SHA and publishes both the floating and SHA-specific GHCR tags owned by `Shanfu2021`.

No credential is committed or embedded in a remote URL. Authentication material is used only at command execution time and must be revoked after the task because it was shared in plaintext.

## Failure And Recovery

- Preserve the pre-merge commit and remote branches; never force-push an unknown remote state.
- If upstream advances during the integration, pin this run to `e316ebf5`. A later upstream change is a separate sync after this merge reaches green CI.
- If a GitHub job fails, use its logs to make a focused follow-up commit rather than weakening or skipping the check.
- If the image build fails after CI passes, fix only the Docker/workflow path needed for the image and rerun all checks for the new SHA.
- Do not deploy to a running service as part of this task. The deliverable is merged source plus successful GitHub build artifacts.

## Success Criteria

- `my_feature` contains a merge of `e316ebf5` and retains all listed fork capabilities.
- No unresolved conflict markers or accidental untracked-file additions exist.
- Existing fork migrations are unchanged and the complete migration chain passes on PostgreSQL.
- GitHub `CI` and `Security Scan` succeed for the pushed integration SHA.
- The GitHub-hosted image build succeeds for the same SHA in `Shanfu2021/sub2api`.
